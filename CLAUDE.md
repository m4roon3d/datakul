# Datakul: notes for Claude

Datakul is quest-based learning for data engineering, analysis, science and architecture careers: a static web app,
an AI gateway on Cloudflare Workers, and a D1 database for community picks. Owner: Ramanaa (prefers plain language,
short answers, no jargon).

## Layout

- `web/`: the app, served as static files. Menu: top bar with a Practice drop-down on desktop, bottom bar with a raised Ask button on phones (`tests/nav.py`). Scripts load in this order: config.js, library.js, community.js, problems.js,
  diagrams.js, app.js, pyrunner.js, practice.js, quests.js, exam.js, pwa.js (install, offline, shortcuts). `sw.js` is the
  offline service worker (network first; bump `CACHE` if the saved-file strategy changes) and `manifest.webmanifest` the install details. `admin.html` is the community review page.
- `web/library.js`: the concepts (`C`) and interview questions (`Q`), 225 and 420 as of 28 Oct 2026 and growing weekly.
  Content is written in `content/batches/batchNN.py`, checked with `node content/validate_batch.js <batch.json>` and merged
  with `content/merge_batch.js` (which stamps new concepts with an `nw` date). The syllabus source is
  `content/syllabus.txt`; wave 2 is written in the order of `content/queue.txt`. The weekly update follows
  `docs/weekly-content.md`.
- `web/certs.js` (generated) and `web/exam.js`: exam prep, its own top-level section (Certifications). Question banks are written in
  `content/certs/*.py` (original questions only, from the public exam guide; never real exam content), checked and built
  with `node content/build_certs.mjs`. Readiness = last 10 answers per exam section, ready at 8+ answered and 75%+.
  Study chapters (Schaum-style notes, solved problems, docs links; all seven Databricks DE Associate sections as of 2 Nov 2026) live in `content/certs/study/<cert>.<section>.json`, written by `content/certs/study_*.py`;
  the build validates them and attaches each to its section (`domain.study`). Figures (a section map plus one per key idea, keyed by idea title) are written in `content/certs/study_figs.py` → `content/certs/figs/`, using the `web/diagrams.js` kinds (now also `tree` and `dag`), and must only show facts in the chapter text; the app shows a Study button on sections that have one. Questions can carry
  `more` (a docs.databricks.com link) shown after a wrong answer. Only link docs.databricks.com pages; mark unconfirmed details "check in a workspace".
  `worker/src/certq.js` writes new questions every night into D1 (`cert_q`), served at `/api/certq`; `worker/src/certs-meta.js` is generated by the same build. The owner pauses it or sets the count on the review page.
- `worker/src/index.js`: AI gateway (providers, prompts, fallback). `worker/src/community.js`: layer 2 (collect unanswered
  questions, group nightly, draft, check, review, publish). `worker/migrations/`: D1 schema.
- `worker/src/grader.js` is generated from the grader in `web/app.js` by `node tools/sync-grader.mjs`. Never edit it by hand;
  CI fails if it is out of date.
- `worker/src/cache.js` (migration 0005): saved answers. A grounded first Ask question (library notes, no history, no PII, sharing on) is saved under a hash of the whole prompt, so prompt or card edits start fresh; served again with `x-provider: cache`, kept 30 days, at most 5,000. The review page's AI status tab shows counts and a Clear button. The question text is never stored.
- `worker/src/usage.js`: one D1 row per AI call (never the text) for the review page's AI status tab; free allowances
  in `FREE_LIMITS` need updating when providers change them.
- Accounts (optional, off unless the `GOOGLE_CLIENT_ID` secret is set): `worker/src/accounts.js` (Google token check, sessions,
  progress sync, delete), `web/account.js` (Settings block, merge, sync), `web/privacy.html`, migration 0003. Synced keys are
  listed in `KEYS` in `web/account.js`; add any new learning data there. Device settings never sync. Learner data off the
  device means `web/privacy.html` must be updated first.
- `android/`: the Android app, a Trusted Web Activity around the live site (no code; manifest and resources only), package `app.datakul`.
  `.github/workflows/android.yml` builds the APK (published as a release on main); `android-release.yml` builds the signed Play bundle from
  secrets. `web/.well-known/assetlinks.json` must list the signing key's fingerprint (`tests/android_static.py` and the build check it).
  The debug keystore is committed on purpose; the Play upload key lives only in GitHub secrets. See `docs/android.md`.
- `tools/deploy.mjs`: the deploy, run by `.github/workflows/deploy.yml` on every merge to main.
- `tests/`: `gateway.mjs` and `layer2.mjs` (Node 22, D1 on built-in SQLite), `l2ui.py` (Playwright, needs
  `node tests/l2server.mjs 8788` running; screenshots go to `tests/out/`).

## Commands

- Tests: `node --no-warnings tests/gateway.mjs`, `node --no-warnings tests/layer2.mjs`,
  `node --no-warnings tests/status.mjs`, `node --no-warnings tests/cache.mjs`, then `node tests/l2server.mjs 8788 &` and `python3 tests/l2ui.py`,
  `tests/themes.py`, `tests/teach.py`, `tests/status_ui.py`, `tests/exam.py`, `tests/pwa.py`, `tests/account_ui.py`, `tests/nav.py`, `tests/motion.py`, `tests/cache_ui.py`; also `node --no-warnings tests/accounts.mjs` and `tests/certq.mjs`.
- After changing the grader in `web/app.js`: `node tools/sync-grader.mjs`.
- Every interview question needs a model answer `a` that earns all its key points (`tests/teach.py` checks it); add
  answers to existing questions with `node content/add_model_answers.mjs <answers.json>`.
- All app scripts share one global scope: `node tools/check_globals.mjs` fails if a top-level name is declared twice.
- Brand files: `python3 tools/make_brand.py` (K mark + Space Grotesk wordmark → `brand/`, `web/icons/`, Android icons, inline mark and favicon). Theme test: `python3 tests/themes.py`.

## Rules

- API keys and `ADMIN_TOKEN` live only in GitHub secrets and Cloudflare Worker secrets. Never commit them or put them in `web/`.
- `worker/wrangler.toml` keeps the placeholders (`database_id`, `ALLOWED_ORIGINS = "*"`, `SITE_URL = ""`); the deploy fills
  them in on the runner. `web/config.js` stays empty in the repo; the deploy writes the gateway address.
- Groq's free models change: check console.groq.com/docs/deprecations before adding a model.
- Privacy: questions sent to `/api/miss` are anonymous (PII masked, no IP stored, deleted after 180 days) and learners can opt
  out. Anything new that sends learner data off the device needs the privacy notice updated first.
- Colours come from the theme tokens in `web/index.html` (light, dark, black). Never hard-code a colour in a component;
  check new UI in all three themes and at phone width (the phone header must fit logo, chips and settings).
- Brand: logo K "Data climb" (three rising saffron bars, sky-blue flag, navy tile), tagline "Climb your data career". `python3 tools/make_brand.py` rebuilds every logo file, the web icons, the Android launcher icons, and the mark and favicon inside `web/index.html` and `web/admin.html`. The bar colours are theme tokens `--climb-1..3` (with `--sky` for the flag).
- Motion: helpers live at the top of `web/app.js` (`climbLoader` for every wait, `morph` for card-to-lesson, `buzz` for Android haptics); the splash is inline at the top of `<body>` in `web/index.html` (first open of a session only, never blocks taps). Also: the streak chip flickers and rolls its count when the streak grows (`refreshChrome` in `web/quests.js`); a boss round's first unlock rattles the lock once, used up only when the Quests screen is on show (`bossseen`, device only); `glideTab` slides one highlight under the selected tab. Keep animations short (under about a second; the splash about 1.5 s) and keep everything off under `prefers-reduced-motion` (`tests/motion.py`).
- Concept cards stay short: a takeaway, a diagram where it helps, an example; detail behind disclosures.

## Working agreement

- Branch from the latest `main`, open a PR, wait for CI. **Merge only when Ramanaa says "Merge"** (squash).
- A merge deploys to production. After a merge, check the Deploy run and report the app address from its summary.
- Say what was tested in a browser and what was tested live; never claim live behaviour that was only tested locally.
